01 / THE LAB

I built a controlled AWS environment around an intentionally vulnerable application.

I used OWASP Juice Shop as the target and deployed it alongside a self-hosted GitHub Actions scanner runner, a private SonarQube server and an encrypted PostgreSQL database. The scanner and application were in a public subnet with restricted security groups; SonarQube and RDS were in private subnets.

I used Systems Manager for administration and diagnostics without inbound SSH. VPC endpoints provided private access to selected AWS services. GitHub-hosted jobs used OIDC roles for Terraform, while the AWS runner handled the security scans.

02 / IMMUTABLE BUILDS

I prepared the hosts before deployment and replaced them when a fix was needed.

Three Packer images

I built Ubuntu 24.04 AMIs for Juice Shop, SonarQube and the scanner runner. I installed software, service definitions and hardening during the image build. A temporary builder used an SSH communicator through Systems Manager without an inbound SSH rule.

Terraform in layers

I separated network, database, observability, compute and SonarQube into independent roots with separate state. I first tested layers manually, then moved routine plans and applies into GitHub Actions with OIDC, state locking and approval of saved plans.

When startup or tool permissions failed, I used read-only diagnostics, corrected the image source, rebuilt the AMI and replaced the instance. Packer supports this approach; it does not by itself prevent a running host from being changed.

03 / THE PIPELINE

I tested each workflow on its own, then connected them.

Gitleaks · secret scanning

I scanned repository history and investigated a public-key fingerprint that was reported as a false positive.

SonarQube · SAST

I submitted the matching Juice Shop source to the private SonarQube server and exported an aggregate summary with a separate reporting credential.

Dependency-Check · SCA

I scanned packaged dependencies for known vulnerabilities and recorded limited coverage: the release lacked a top-level lockfile and npm audit was unavailable.

Terraform · reviewed deployment

Plans were saved and reviewed before apply. Network ran first; dependent layers followed, with independent work in parallel where possible.

OWASP ZAP · DAST

After deployment, ZAP ran a bounded unauthenticated spider and active scan against the approved Juice Shop target. I retained the coverage limitation with its results.

The scanner runner and SonarQube had to be bootstrapped before the combined workflow’s pre-deployment scans. I kept the standalone workflows for testing and investigation.

04 / TROUBLESHOOTING

The failures helped me strengthen the build and the reporting.

SonarQube startup

The service did not become ready because its runtime user could not execute the installed AWS CLI. I inspected permissions, corrected the image build, rebuilt the AMI and verified the replacement returned an UP status.

Runner capacity and tools

A scan exhausted the original runner’s memory. I changed its instance size and replaced it through Terraform. Missing Node.js and npm were added to a rebuilt runner image before the dependency workflow was retested.

Terraform state and IAM

I investigated stale saved plans, a state lock and an existing database after backend changes. Network recreation also changed VPC and subnet IDs used by the separately bootstrapped apply-role policy; that reconciliation remained a manual gap.

Scan execution versus findings

A Dependency-Check run produced reports but ended with an execution error. I treated that as a failure rather than a clean result, investigated it and retained the eventual limited-coverage notice.

05 / OUTCOME & EVIDENCE

A combined run completed; its findings and limitations stayed visible.

The combined workflow completed with the separate secret, SAST, SCA, reviewed Terraform and DAST stages. GitHub Actions retained scan artifacts, while CloudWatch and SNS received aggregate summaries rather than an email for each finding.

Juice Shop is deliberately vulnerable, so findings remained report-only. A successful job means the workflow completed; it does not mean the application has no vulnerabilities. The lab demonstrates security controls and automation, not a claim of production readiness.

Recover the IAM user's console password

I wanted to carry out the lab as the mds-devsecops-lab IAM user and use aws login to obtain temporary CLI credentials. I could not sign in as that user with the console password I had available, so I first needed to reset the password. Once I had restored access, I could sign in as the IAM user and continue the lab with that identity.

I chose aws login because its browser-based flow gives the CLI short-lived credentials and manages their refresh during the login session. Their limited lifetime reduces how long exposed credentials can be used, although they still need protection and are subject to the IAM user's permissions. When the CLI session expires, I can sign in again; an expired session alone does not require a password reset. AWS explains the login flow.

Another option is to enter IAM access keys through the basic aws configure prompt. I avoided long-term keys for this lab because the CLI stores supplied keys in a local credentials file, where they could be exposed if the file or a backup were copied or committed. Unlike temporary credentials, IAM user access keys do not expire automatically and must be managed and revoked when needed. The concern is the use of long-term keys: aws configure can also set non-secret options, and aws configure sso can set up temporary credentials. AWS CLI configure reference, AWS IAM credential guidance.

To recover the IAM user's password, I used my existing root-recovery profile for this one recovery session. The command opened a browser sign-in link, which I followed to authenticate as the AWS account root user.

aws login --profile root-recovery

I checked the caller ARN before continuing. This confirms the AWS identity actually in use, rather than relying on the local profile name.

aws sts get-caller-identity \
  --profile root-recovery \
  --query Arn \
  --output text

I checked that the returned ARN ended in :root before using the recovery profile. A profile name is only a local label; a profile called root-recovery can still point to a different identity. This was the recovery route I used when I could not access my IAM account, not a requirement to sign in as root whenever an IAM user's CLI session expires.

I then used this Python-assisted command to set a new console password for mds-devsecops-lab. It prompts without echoing the password, checks the confirmation, writes the request into a restricted temporary file, and removes that file on exit. I did not paste a real password into the command or commit one to the repository.

(
  set -e
  umask 077

  login_input="$(mktemp)"
  trap 'rm -f "$login_input"' EXIT

  python3 - "$login_input" <<'PY'
import getpass
import json
import sys

password = getpass.getpass("New password for mds-devsecops-lab: ")
confirmation = getpass.getpass("Enter it again: ")

if not password or password != confirmation:
    raise SystemExit("Passwords are empty or do not match. Nothing changed.")

with open(sys.argv[1], "w") as file:
    json.dump({
        "UserName": "mds-devsecops-lab",
        "Password": password,
        "PasswordResetRequired": False
    }, file)
PY

  aws iam update-login-profile \
    --cli-input-json "file://$login_input" \
    --profile root-recovery \
    --no-cli-auto-prompt

  printf 'IAM user password updated successfully.\n'
)

The important distinction is that this script resets the IAM console password. It does not generate short-lived API credentials, renew an expired CLI session or reset the root password. AWS documents that behaviour in update-login-profile. An administrator authorized to reset IAM login profiles can perform this operation too; it is not inherently a root-only task.

Why I kept root out of routine lab work

A principle reinforced by my AWS security studies was to keep the root identity protected and avoid it for ordinary administration. Root has account-wide powers, including operations reserved to root; accidental use or compromise therefore has a particularly large impact. I documented my root recovery as an exception and moved back to a non-root identity afterward. AWS recommends protecting root, using it only where required, enabling MFA and avoiding root access keys in its root-user guidance.

For this lab I used my IAM user for the administrative work I was authorized to perform instead of deploying as root. Administrative permissions are still powerful: AdministratorAccess is not least privilege, and replacing root with an unrestricted user does not remove that risk. I used separate scoped roles for automation. AWS's broader recommendation is federated human access with temporary credentials where possible, workload roles, MFA and least privilege—not permanently granting every operator administrator permissions. See IAM security best practices.

2. Install Packer and the Session Manager plugin

With IAM access recovered and the active AWS identity checked, I could prepare the local tools for the image builds.

Packer is an image-building tool that creates machine images from repeatable build instructions. I used it to prepare the operating system, software, services and hardening in Amazon Machine Images (AMIs) before Terraform deployed the instances. This supported the immutable infrastructure principle I wanted to demonstrate: once a host was deployed, I treated its installed software and baseline configuration as fixed. When something needed changing, I updated the build instructions, rebuilt the AMI and replaced the instance instead of configuring it by hand after deployment.

Packer does not itself prevent someone from changing a running instance; that was a practice I followed in the lab. I still used read-only checks to diagnose problems, and the baked startup code could retrieve environment-specific settings and credentials. The local Session Manager plugin let Packer tunnel its SSH connection to a temporary builder through SSM without an inbound SSH rule.

7. Create a no-ingress Packer security group

The network inspection showed where the builder would run. I next restricted its traffic with a dedicated security group.

The temporary builder needed outbound download and management access, not inbound administration. Its dedicated security group made that boundary explicit.

I stopped using the default security group for builds and created a dedicated group with no inbound rules. Its outbound rules allowed TCP 80 for package mirrors and TCP 443 for SSM and downloads. Packer used its SSH communicator inside an SSM tunnel; this lab did not open public port 22. The temporary communicator is still SSH internally, so I do not describe it as an SSH-free Packer protocol.

12. Split Terraform into independent roots

The images defined what would run on each host; Terraform would now define the AWS resources around those hosts.

I introduced Terraform to describe the AWS infrastructure surrounding the images. Separate roots made ownership, state and dependency order explicit.

I created five separate Terraform root directories. Each root is an independently executed configuration with its own state: network owns the VPC, subnets, routes and security groups; database owns RDS; observability owns log groups and SNS; compute owns Juice Shop and the scanner runner; and sonarqube owns the SonarQube instance. At this point only network and database contained files—empty directories were not missing Git commits.

I made this choice to give each layer a clear responsibility and to limit the scope of routine changes. For example, I can review a change to log groups in the observability root without placing every network and database resource in the same plan. Each root has its own state key and lock, so unrelated roots can run independently where their dependencies allow it. Separate state does not isolate the resources themselves: changing or destroying a network can still affect everything that depends on it.

This distinction matters as an environment grows. A single root managing thousands of resources can produce a large state, take longer to refresh and plan, and create a review with many possible changes. Its state lock can also make unrelated operations wait on the same configuration. A broad apply or a mistake in that root may affect a larger part of the environment. Dividing infrastructure into sensible ownership and lifecycle boundaries can make plans easier to review, reduce lock contention and narrow the scope of an operation. The actual performance and risk depend on the resources, provider operations and how the boundaries are designed; separate roots are not automatically faster or safer in every case.

A long Terraform file and a large Terraform state are different problems. Terraform combines all .tf files in the same directory into one root configuration. Splitting one long file into network.tf, routing.tf and other files improves readability, but those files still share one state and one lock. Creating separate root directories with separately configured backends is what gives each layer its own state.

The trade-off is coordination. Downstream roots need the correct upstream outputs, deployment order and access to the required state or published outputs. I deployed the network first, then the layers that depend on it, and allowed independent work to run in parallel where the workflow supported it. In production I would choose boundaries around ownership, access and lifecycle rather than create a separate state for every resource, and I would protect state because it can contain sensitive information.

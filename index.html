06 / FIELD NOTES

Technical thinking.
Explained clearly.

Short, practical notes that translate cloud-security decisions into language an engineer, recruiter, or non-specialist stakeholder can follow.

FIELD NOTE 01 / AWS IDENTITY / 4 MIN READ

Why keyless AWS delivery starts with OIDC

Replacing stored AWS access keys with short-lived, scoped credentials removes a common secret-management burden, but the trust policy is the real security boundary.

Read the field note +

The risk

Long-lived access keys can be copied, exposed in logs, or retained after a workflow changes. Rotation helps, but it does not remove the standing credential or prove which workflow used it.

The design

With GitHub OIDC, a workflow requests a short-lived token and AWS evaluates its claims before allowing the workflow to assume a role. The role should trust only the intended repository, branch, or environment.

What I would validate

  • An approved branch can assume the deployment role.
  • An untrusted branch, fork, or repository is denied.
  • The role permissions cover only the required deployment actions.
  • CloudTrail records the assumed-role session for investigation.

Takeaway

OIDC removes static keys; precise claims, least-privilege permissions, protected environments, and audit evidence make the design secure.

FIELD NOTE 02 / PORTFOLIO EVIDENCE / 3 MIN READ

A cloud-security screenshot is not proof

A dashboard can show that a tool ran. A strong case study explains the decision, reproduces the control, tests failure paths, and preserves the evidence needed to defend the result.

Read the field note +

Start with a security question

"I enabled GuardDuty" describes an action. Asking how quickly a high-confidence finding can become an actionable, reversible response creates a problem that can be designed and tested.

Show the reasoning

The architecture should identify trust boundaries, data flow, scoped permissions, failure handling, and the trade-offs behind each control. Code matters, but the explanation shows whether the design is understood.

Test more than the happy path

  • Prove the expected action succeeds.
  • Prove unauthorized or unsafe actions fail.
  • Capture logs, findings, and rollback evidence.
  • Document what failed and what should change next.

Takeaway

Recruiter-ready proof connects a security problem to a repeatable build, observable test results, and an honest reflection.

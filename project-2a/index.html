PROJECT 02A / LOCAL APPLICATION SECURITY ASSESSMENT

One training app.
Four assessment views.

I assessed OWASP Juice Shop on an isolated target server, looking at its dependencies, source code, running web application, and APIs. I documented what the tools and focused manual checks showed so the development and service owners could decide and carry out remediation.

01 / THE LAB

I continued in the three-node lab I had already hardened for Project 1A.

I used OWASP Juice Shop, an intentionally vulnerable training application designed for security practice. It gave me a controlled target with realistic web and API routes. The result describes this version of the lab application; I do not treat every deliberate training weakness as evidence of a production defect.

The workload ran in Docker on the target server. I used WSL as my workstation for the source checkout and assessment tools, and the hardened admin node as the SSH hop to the hardened target node. The three-node arrangement carried forward the isolation and access controls from Project 1A Linux Server Hardening. I transferred the container image into the lab rather than opening the target to unrestricted internet access.

During setup I hit practical issues: Docker was initially unavailable to my WSL account, the target had no Docker CLI, an image pull failed when the target could not resolve Docker Hub, and the first SSH tunnel attempts reused port 3000 or pointed to a stopped service. I checked each layer separately—engine, container, bridge, host route, and tunnel—before continuing. The working assessment tunnel was on local port 3001.

02 / SOFTWARE COMPOSITION ANALYSIS

I used Snyk Open Source to identify vulnerable dependencies.

SCA examined the package manifest and dependency tree. My first run could not proceed because node_modules and a committed lockfile were missing. After installing Node.js and npm in WSL, I installed the dependencies without running package lifecycle scripts and repeated the scan. Snyk reported 87 advisory/path entries: 2 Critical, 36 High, 47 Medium, and 2 Low. I recorded individual advisories and dependency paths, preserving repeated paths where the source output did so.

cd ~/project-2a/juice-shop-source
npm install --ignore-scripts
"$HOME/.local/bin/snyk" test --dev

The assessment report separates scanner severity from my risk triage. The package results are evidence for dependency owners to review and update; I did not upgrade packages or modify the application in this stage.

03 / STATIC APPLICATION SECURITY TESTING

I scanned the source in a white-box assessment.

SAST analyzes source code without requiring the application to be running. In this lab I used the matching Juice Shop v20.3.0 source checkout, so Snyk Code could report source paths and line numbers. This is the white-box view. My first attempt returned no findings because Snyk Code was disabled for the selected organization; after I enabled it, the scan returned 306 findings: 26 High, 11 Medium, and 269 Low. I noted that 240 Low records were in test/ paths for owner triage.

cd ~/project-2a/juice-shop-source
"$HOME/.local/bin/snyk" code test

I reviewed and documented the individual results, including their source locations. Because Juice Shop deliberately includes vulnerable training code and test fixtures, I treated each result as a finding to interpret in context rather than an automatic production risk. Source owners would decide which findings applied to a real deployment.

04 / DYNAMIC APPLICATION SECURITY TESTING

I tested the running service in a black-box view.

DAST sends requests to a running application and judges its observable responses without relying on source code. That is the black-box view for this lab: OWASP ZAP reached the Juice Shop instance through the local SSH tunnel. I ran baseline and AJAX-enabled baseline scans, then used ZAP’s API to compare the URL lists from its traditional Spider and AJAX Spider. The saved comparison contained 91 AJAX URLs, 94 traditional URLs, 10 exact matches, and 81 AJAX-only URL strings. Changing Socket.IO query values contributed to the URL-string counts, so I did not treat those values as 81 distinct routes.

chmod 777 ~/project-2a/zap-reports
docker run --rm -t -e HOME=/tmp \
  -v "$HOME/project-2a/zap-reports:/zap/wrk:rw" \
  zaproxy/zap-stable \
  zap-baseline.py -t http://host.docker.internal:3000 -r juice-shop-baseline.html
docker run --rm -t -e HOME=/tmp \
  -v "$HOME/project-2a/zap-reports:/zap/wrk:rw" \
  zaproxy/zap-stable \
  zap-baseline.py -t http://host.docker.internal:3000 -j -r juice-shop-ajax.html

The generic baseline produced 116 URLs, 0 FAIL alerts, 3 warning types, and 58 PASS checks; the AJAX-enabled baseline produced 35 URLs, 0 FAIL alerts, 3 warning types, and 58 PASS checks. I also used ZAP’s API Scan with an eight-route, GET-only OpenAPI definition. It imported 16 URLs and reported 53 total URLs, 108 PASS checks, 0 FAIL alerts, and 7 warning types; the report listed 37 GET endpoints. Its generated probes were active scanner traffic, so I reviewed those alerts separately and checked relevant responses against source and manual evidence. Scanner output alone did not establish exploitability.

05 / API SECURITY

I combined ZAP’s API scan with focused, read-only checks.

ZAP’s API scan covered the documented API surface. I used small Python helpers to compare crawled URL lists, inspect configuration property names without printing values, and review saved ZAP alerts. For authorization, I tested two lab accounts against their own baskets and then against each other’s basket IDs. A separate helper checked whether an unsigned token was accepted for a read-only basket request. I did not change basket contents or use these checks against a production service.

The two-account check returned each other account’s basket, which I recorded as a confirmed lab broken object-level authorization finding. The unsigned-token request was accepted for a read-only basket request. I also recorded ZAP’s product-search SQL injection alert and confirmed unsafe query construction in the source; I did not demonstrate data extraction. I kept these manual checks separate from ZAP’s scanner alerts, even where the endpoints overlapped, because they use different evidence and methods.

The helpers prompt for test-account credentials where required and avoid recording passwords or tokens in the evidence. The source review and observed responses informed triage; endpoints that returned expected public catalog or version data were not called vulnerabilities solely because they returned HTTP 200.

06 / REPORTING + OWNERSHIP

I prepared the evidence for the people responsible for the fixes.

My role in this lab was to assess, validate, document, and route findings. I did not write Juice Shop and I did not remediate its code. In a working team, I would give development or service owners clear reproduction evidence, impact, and acceptance criteria, then track the risk and follow up on verification after their change.

The repository contains the consolidated assessment inventory, individual SCA, SAST, DAST, and manual API findings, a triage review, and a risk register. I also created six remediation issues for actionable API findings. This demonstrates the handoff from assessment to engineering ownership without presenting unverified scanner alerts as confirmed defects.

OWASP classifications

I used OWASP categories to describe the application and API risk types in the assessment record. The categories helped explain what the findings represented; they did not replace evidence or determine remediation ownership.

NIST CSF 2.0 in the workflow

I used the risk register to show how findings fit an organizational process: identify and assess risk, assign an owner, track treatment, and retain verification evidence. Framework mapping belongs in that governance view where useful, rather than cluttering each engineering issue.

This was a local training assessment, not a production audit or claim of compliance. Project 2B is the separate planned cloud application and API security track.

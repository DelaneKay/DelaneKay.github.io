01 / THE SITUATION

I started with a server that was already running—and a fault I had not yet uncovered.

Meridian Digital Services is fictional. Its reporting worker was meant to read customer records and produce reports, logs, and exports. The target was an existing Ubuntu server, not a clean machine I had just built.

The exercise pointed to an AI-generated package called mds-induction.zip as the source of the unsafe setup. I had not examined it, so I did not know what it had changed. Finding out what was actually present on the server became the investigation. The lab and all records were synthetic; this was a controlled simulation, not a real breach.

02 / THE LAB

I separated the control point from the target before investigating.

Two Ubuntu VMs on my Windows laptop

mds-admin-01 was my Ansible control server. mds-ubuntu-server-01 was the target running the reporting workload. I used WSL on the same laptop for SSH and the Lynis transfer; WSL was not a third VM.

The admin VM had a host-only management connection and an adapter on VirtualBox’s internal network, mds-sec-lab. The target was attached to that internal lab network. This segmentation gave me a distinct management path and kept the target inside the lab design while I worked.

Windows laptopVirtualBoxHost-only managementInternal network: mds-sec-lab

Why this setup mattered

A separate control VM mirrors a common operations pattern: administration happens from a managed point, while the workload sits on its own target. Keeping the exercise in local virtual machines reduced the chance of exposing a deliberately weak server to a real network.

SSH protected remote administration and file transfer in transit. I used separate SSH keys for WSL-to-admin and admin-to-target connections. I retained the address 192.168.77.10 in Ansible’s target inventory.

Moving the induction archive

I copied the ZIP from Windows PowerShell to the admin VM using SCP over SSH. This is the command shown in my captured session:

scp "$env:USERPROFILE\Downloads\mds-induction.zip" mdsadmin@192.168.56.101:~/

I ran this in PowerShell, so I used the Windows user-folder variable rather than a WSL /mnt/c path.

Checking transfer integrity

I compared SHA-256 fingerprints at the transfer points. Matching hashes showed that the copies contained the same bytes when checked; the hash did not prove the archive was safe or who created it.

f23cb7326c3fb42868286a72705d7f25cef80cb896d8ff1739193d94f0e18c07

SSH was my administration path

I used two separate key-based connections: mds_admin_ed25519 from WSL to mds-admin-01, then mds_target_ed25519 from the admin VM to mds-ubuntu-server-01. Keeping the hops separate made the control path clear: WSL reached the control VM on its host-only address, and Ansible reached the target on the internal lab network.

At a first connection, SSH asked me to trust the host key; I verified the intended host before continuing. I did not retain the key-generation commands, so I have not reconstructed them here. SCP used SSH encryption for the file transfer, while the SHA-256 comparison provided a separate integrity check.

What the induction package was for

The archive contained lab.py, session.json, and assets/session.py. It was designed to establish a synthetic starting scenario with reporting records, logs, archives, and a permissive service. I used its documented workflow as context for the exercise:

python3 lab.py preflight --ask-become-pass
python3 lab.py deploy --ask-become-pass
python3 lab.py verify --ask-become-pass

preflight checks the control VM, Ansible, inventory, network, and SSH/sudo access; deploy is intended to seed the lab workload; and verify checks the expected setup. The package recommended a pre-deployment VirtualBox snapshot named 01-Pre-Vulnerable-Lab. I did not preserve a successful deployment transcript, so these commands describe the package workflow rather than a complete captured result from the target.

03 / EVIDENCE FIRST

I used a repeatable inspection approach because I did not yet know what was wrong.

I did not yet know which settings were unsafe, so I followed a deliberate sequence: map users and privileges; trace access to sensitive files; compare active and persistent services; inspect scheduled work; identify listening ports and firewall policy; then run Lynis before changing anything. I started with read-only Linux tools so I could establish what the server was doing before remediation. Unfamiliar service names and open ports were investigation leads, not proof of compromise.

Map accounts and privileges

I reviewed users, groups, UID 0 accounts, and sudo rights to distinguish service identities from people who could administer the host.

Trace file access

I checked ownership and permissions on customer records and along parent directories. A file’s mode only tells part of the story if users can alter the directory containing it.

Understand services and persistence

I compared running services with enabled units, inspected timers and cron, then checked the purpose and runtime account of anything unexpected.

Review ports and firewall policy

I identified listening sockets, bind addresses, and owning processes, then inspected firewall rules. I assessed each listener against its purpose before deciding whether it needed a change.

Use Lynis as a second assessment

I ran Lynis 3.1.7 on the isolated target before making changes. Its suggestions added coverage, while direct observations determined which changes fit the service.

Account and privilege reviewRead-only inspection
getent passwd
getent group
id mdsadmin
sudo -l -U mdsadmin

The retained output showed root at UID 0, mdsadmin at UID 1000 with a Bash shell, and nobody at UID 65534 with a non-login shell. No additional UID-0 account appeared in the enumeration. mdsadmin had broad sudo rights; I recorded that as an administrative privilege to assess against the account’s role, not as proof of misuse.

File path and permissionsRead-only inspection
namei -l /srv/mds/records/customers.csv
stat /srv/mds/records/customers.csv

The customer file initially had mode 0666 and was owned by root:root, allowing ordinary local accounts that could reach it to change its contents. Its parent directories were root-owned with mode 0755, so users could not write to those directories. The risky permission was on the file itself.

Services and boot persistence

I compared what was running now with what systemd was configured to start at boot. This distinction matters: a running service may be activated another way, and an enabled service can be stopped at the moment of inspection.

systemctl list-units --type=service --state=running --no-pager
systemctl list-unit-files --type=service --state=enabled --no-pager

The running inventory included cron, ssh, systemd-logind, systemd-udevd, user@1000, and Meridian’s mds-reports. The reporting unit was also enabled, but launched /usr/bin/sleep infinity, a placeholder process. SSH was running but absent from the enabled list, so its activation mechanism remained unconfirmed. I investigated purpose and configuration instead of treating names as suspicious: logind manages sessions, udev handles device events, and user@1000 is the user systemd manager for UID 1000.

Cron and systemd timers

Scheduled work can run with elevated privileges or recur after reboot, so I reviewed the system crontab, cron directories, systemd timers, and a relevant timer journal.

cat /etc/crontab
ls -la /etc/cron.d /etc/cron.daily /etc/cron.weekly
systemctl list-timers --all --no-pager
journalctl -b -u e2scrub_all.service --no-pager

The inspected cron entries and directories were root-owned without group or other write access. e2scrub_all had cron fallback entries and a systemd timer; the timer was inactive and the reviewed current-boot journal had no entries. That did not establish successful execution, and I treated it as a lead to understand rather than malicious activity.

Listening ports and their owners

I checked listening TCP/UDP sockets with process details so I could relate each port to a service, bind address, and intended client before considering whether to restrict it.

sudo ss -lntup

DNS on port 53 and Chrony on port 323 were bound to loopback. SSH listened on port 22 on local IPv4 and IPv6 addresses. SSH was needed for administration, and SSH hardening belongs to a separate proactive project. A port being open does not by itself mean it is unnecessary.

Firewall policy

I inspected UFW, nftables, and legacy IPv4 and IPv6 firewall listings to understand the filtering actually present on the host.

sudo ufw status verbose
sudo nft list ruleset
sudo iptables -L -n -v
sudo ip6tables -L -n -v

UFW was inactive, and the recorded nftables and legacy listings were empty. Lynis later corroborated that the host firewall was inactive. I documented that baseline but did not change firewall policy in this reactive data-and-service hardening project.

04 / LYNIS BASELINE

I ran Lynis on the target after the built-in checks and before remediation.

Lynis complemented the read-only Linux checks with a broader host audit. I ran it on mds-ubuntu-server-01, the isolated target, not on mds-admin-01, which was my Ansible control server. Because the target was isolated, I used WSL to obtain the tagged Lynis source and transferred it through the admin VM using the two SSH hops.

I compared SHA-256 fingerprints at the transfer points. Matching fingerprints gave me evidence that the copies contained the same bytes at those points; checksums do not establish that a package is trusted or safe.

From WSL to the admin VM

I cloned the Lynis 3.1.7 source tag and transferred the archive to the admin VM using my WSL-to-admin key. The archive-creation command was not preserved, so this block shows the captured clone, hash, and transfer steps only.

git clone --depth 1 --branch 3.1.7 https://github.com/CISOfy/lynis.git ~/lynis-3.1.7
sha256sum ~/lynis-3.1.7.tar.gz
scp -i ~/.ssh/mds_admin_ed25519 ~/lynis-3.1.7.tar.gz mdsadmin@192.168.56.101:~/

The archive fingerprint recorded for the transfer was c0808d6b9e9a784ba912a32b2b43052d57ce0a2a2741735194969a3021ab739e.

From admin to the isolated target

On the control VM, I checked the archive hash again and used the target-specific SSH key to copy it to the server being audited.

sha256sum ~/lynis-3.1.7.tar.gz
scp -i ~/.ssh/mds_target_ed25519 ~/lynis-3.1.7.tar.gz mdsadmin@192.168.77.10:~/

This two-hop path kept the admin VM between my local WSL environment and the target's internal lab network.

Checking and running the source tree

Lynis was a manually transferred source tree rather than an installed Ubuntu package. The first attempt from the home-directory copy could not find its include/ directory. A later elevated audit also stopped because include/functions was owned by mdsadmin; Lynis required the support file to be root-owned before running with elevated privileges. I cancelled that attempt, checked the source installation, and used a root-owned copy under /opt. The exact preparation commands were not preserved.

dpkg-query -W lynis
cd /opt/lynis-3.1.7
./lynis show version
sudo ./lynis audit system --quick

The package query returned no installed package; the version check reported 3.1.7. The final directory listings showed the Lynis files owned by root:root.

Preserving the baseline report

I saved the audit log and report under a root-only directory before another scan so the baseline remained available for comparison and ordinary accounts could not read it.

sudo install -d -m 0700 /root/mds-audit-baseline
sudo cp -n /var/log/lynis.log /var/log/lynis-report.dat /root/mds-audit-baseline/
sudo sha256sum /var/log/lynis.log /root/mds-audit-baseline/lynis.log /var/log/lynis-report.dat /root/mds-audit-baseline/lynis-report.dat

The matching hashes showed the saved logs were identical to the source files at copy time. The copy command displayed a portability warning but completed successfully.

What I did with Lynis findings

I used its suggestions as prompts to investigate, not as automatic remediation instructions. One warning flagged /etc/sudoers.d because its mode was 0755. I checked that the directory was owned by root and that group and other users had no write bits. Only root could write there, so I recorded the warning and left it unchanged pending comparison with expected package and local policy.

The overall score changed little after my work because Lynis assesses many host-level areas outside the project scope. I demonstrated the controls I actually changed through ownership, permissions, effective systemd settings, service state, access checks, and an idempotent Ansible rerun rather than claiming a large score increase.

05 / FINDINGS

I compared the unsafe starting state with what the service actually needed.

After the native checks and Lynis baseline, I reviewed the service unit alongside the data paths it used. The issue was not a single scanner score: the customer file allowed broad local writes, logs and archives had looser access than the worker needed, and the worker had a generic identity with few systemd restrictions.

These were synthetic lab files and a fictional reporting workload. I chose controls around confidentiality and least privilege while preserving the worker's required access and an administrator's ability to override through sudo/root.

Observed stateRisk I assessedControl I selected
customers.csv: root:root, 0666Any local user able to traverse the path could alter the file contents.Dedicated reporting ownership and 0600 access.
logs/: 0755; application.log: 0666Excessive access could expose or change operational records.Reporting-account ownership; directory 0700, file 0600.
archive/: 0777; export.csv: 0644Everyone could modify the directory contents; exported data was broadly readable.Reporting-account ownership; directory 0700, file 0600.
Service started as nobody:nogroup; UMask=0000; weak sandbox settingsA generic identity and broad runtime view made access harder to scope and contained less effectively.mds-reports identity and systemd restrictions with explicit writable paths.

Least privilege needed a service identity

The worker had to keep routine access to create reports and update its inputs, while ordinary local users should not have the same access. A dedicated account makes ownership and permissions express that boundary directly. An authorized administrator can still use sudo/root when an override is needed.

The service needed a smaller filesystem view

File modes control access to particular paths; systemd's filesystem restrictions limit the service's broader runtime view. I used both layers so the worker could write to its intended data directories while most of the system remained read-only from its service namespace.

06 / CONTROLLED CHANGES

I turned the findings into small, reviewable Ansible playbooks.

I chose Ansible because it was already available on my admin VM and could manage the isolated target over SSH. A playbook records the desired state in YAML, applies it consistently, and can be run again to detect drift. That repeatability is useful in DevSecOps: it reduces manual variation and makes security changes reviewable. Automation did not choose the right policy for me—I had to understand the risk and verify the result.

Each playbook asserted that the target address was 192.168.77.10 before applying privileged changes. I kept the work in separate files so each control area could be reviewed and rerun independently.

I first checked YAML syntax, SSH reachability, and privilege escalation. Syntax checking validates the playbook structure without changing the server; Ansible's ping module checks the Ansible connection and remote Python availability (it is not an ICMP ping); the final check confirms the become path before privileged tasks.

Pre-flight checks from the admin VMBefore remediation
ansible-playbook -i inventory/hosts.ini harden.yml --syntax-check
ansible -i inventory/hosts.ini mds-ubuntu-server-01 -m ansible.builtin.ping
ansible -i inventory/hosts.ini mds-ubuntu-server-01 -b --ask-become-pass -m ansible.builtin.command -a "id"

IDENTITY + CUSTOMER DATA

harden.yml

I created mds-reports as a system account with no home directory and a non-login shell. A systemd drop-in ran the worker as that account, then Ansible set customers.csv to mds-reports:mds-reports with mode 0600.

This applied least privilege and confidentiality: the service retained routine read/write access, while ordinary mdsadmin lost direct access. The playbook tested both service access and denied admin access; authorized administrators could still use sudo/root for an override. The file itself was mode 0600, so I later called out that deletion/replacement also depends on parent-directory permissions.

LOGS + ARCHIVES

data-files.yml

I restricted the logs and archive directories to mode 0700 and their files to 0600, owned by the reporting account. I added the records, logs, and archive paths to the service’s writable list so ProtectSystem=strict and the worker's application needs could work together. The playbook was separate from harden.yml, so each policy area could be reviewed and rerun independently.

SYSTEMD DEFENCE IN DEPTH

I restricted the worker’s runtime environment as well as its file permissions.

NoNewPrivileges=true

Prevented the service from gaining additional privileges through execution, such as setuid programs. This does not itself prevent writes allowed by file permissions.

UMask=0027

Removed group-write and other-user permissions by default on new files and directories. It does not change existing file modes.

PrivateTmp=true

Gave the service a private view of temporary directories.

ProtectSystem=strict + ProtectHome=true

Made most system paths read-only to the worker and hid home directories in its service view.

ReadWritePaths=…

Allowed writes to the records, logs, and archive paths required by the worker within its systemd filesystem view.

07 / PROOF + REFLECTION

I checked both the allowed path and the denied path.

A successful playbook run alone would not prove that access was correct or that the worker remained healthy. I checked the effective systemd settings, ownership and modes, service state, and actual access results. The worker could read and write the customer file; ordinary mdsadmin could do neither. The mock service stayed active and wrote a synthetic report.

Verification checksObserved on the target through Ansible
systemctl is-active mds-reports.service
systemctl show mds-reports.service -p User -p Group -p MainPID
systemctl show mds-reports.service -p UMask -p NoNewPrivileges -p PrivateTmp -p ProtectSystem -p ProtectHome -p ReadWritePaths
namei -l /srv/mds/records/customers.csv

The effective service settings showed User=mds-reports, Group=mds-reports, UMask=0027, NoNewPrivileges=yes, PrivateTmp=yes, ProtectSystem=strict, ProtectHome=yes, and writable paths for records, logs, and archives. The service remained active. Before switching to the mock worker, I also used ps to confirm the placeholder process ran as mds-reports.

Mock worker run: synthetic report created; service and denial checks passed Idempotent rerun: no further changes required
Access testsRun with become because runuser needs root
runuser -u mds-reports -- test -r /srv/mds/records/customers.csv
runuser -u mds-reports -- test -w /srv/mds/records/customers.csv
runuser -u mdsadmin -- test -r /srv/mds/records/customers.csv
runuser -u mdsadmin -- test -w /srv/mds/records/customers.csv

I ran these tests through Ansible with privilege escalation because an ordinary remote account cannot use runuser to switch identities. The reporting account's read and write checks passed. The ordinary-admin checks returned permission-denied status; the playbooks treat that expected denial as a successful security check.

The first playbook runs showed changes while I was adding controls. After the configuration settled, rerunning mock-worker.yml reported changed=0, which showed Ansible found the target in the desired state. The generated message was labelled LAB MOCK REPORT - synthetic data only; the mock worker did not process customer data.

Verification boundaries

Mode 0600 blocks ordinary users from opening the file directly, but deletion or replacement also depends on permissions on the parent directory. The published checks verified file read/write access, not deletion behavior.

What the mock test demonstrated

The report's existence and timestamp, active service state, and denied admin access demonstrated the synthetic worker path. The test did not prove a fresh report if an older file already existed, nor did it test every forbidden write from inside each systemd isolation boundary.

What the verification establishedObserved in the lab

Access still worked where required

The dedicated service identity retained the file access needed by the workload. The service was active and the synthetic worker produced a labelled report.

Ordinary access was removed

The mdsadmin account could not directly read or write the protected customer and mock-report files. The Ansible rerun reported changed=0.

Security principles behind my choices

Segmentation

The internal VirtualBox network separated the lab target from the management path and limited unnecessary exposure.

Integrity

SHA-256 comparisons checked that transferred archives matched across hops; they did not establish trust or provenance.

Least privilege

A dedicated service identity and restrictive file modes reduced routine access to customer data.

Defence in depth

Unix permissions and systemd sandbox controls limited access at more than one layer.

These choices draw on foundational concepts covered in ISC2 Certified in Cybersecurity and the Google Cybersecurity Certificate, with defence-in-depth and segmentation themes also familiar from AWS Security Specialty learning. I applied those ideas using local Linux controls; I did not use AWS services or claim certification through this project.

What this project did—and did not—claim

This was a reactive Linux hardening exercise on a fictional workload in a local VirtualBox lab. I used Lynis as an assessment aid and verified specific access and service outcomes; I do not claim a large Lynis score improvement because the fixes addressed a focused service and data scope.

SSH provided my administration and file-transfer path. I inspected SSH and firewall state but did not harden either here; that belongs to the separate proactive cloud-server project. I did not install auditd or build a production reporting application. Those are outside this project's completed scope.
